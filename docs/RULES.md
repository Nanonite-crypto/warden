# YARA rules

The second detection layer runs YARA rules over file content. This document
covers what the layer does, where its rules come from, which rules are left
out and why, how a rule match becomes a verdict, and the rule bundle file
format.

The engine underneath is [YARA-X](https://virustotal.github.io/yara-x/),
VirusTotal's implementation of YARA in Rust. The layer lives in the
`warden-yara` crate.

## Why a second layer

A hash signature matches one exact file. Add a line break and the hash is a
different one. A YARA rule describes byte patterns and file structure
instead, so it keeps matching when a file has been changed, repacked or
rebuilt. The price is speed: every rule has to be checked against every
byte, where a hash lookup is a few dozen nanoseconds.
[BENCHMARKS.md](BENCHMARKS.md) has the measurements.

Warden shows the difference with the EICAR test file. The plain 68-byte
file is known by hash. The same file with a line break added has another
hash and is caught only by the built-in rule:

```
warden eicar write demo --kind all
warden scan demo
```

## Where rules come from

**Built in.** One rule ships inside the program:
[`crates/warden-yara/rules/builtin.yar`](../crates/warden-yara/rules/builtin.yar).
It detects the EICAR test file by its definition: the 68 characters at the
start of the file, followed by nothing but whitespace, 128 bytes at most.
Built-in rules cover test files only.

**Rule bundles.** Everything else comes from rule files you choose.
`warden rules build` compiles them into a bundle, and `warden scan --rules`
uses it:

```
warden rules build my-rules.yar a-folder-of-rules\ a-package.zip --out rules.wrb
warden rules info rules.wrb
warden scan C:\Users\me\Downloads --rules rules.wrb
```

A rule that does not compile is left out and counted; it does not stop the
build. `--show-skipped` lists the rules that were left out with the reason.
The built-in rules are part of every bundle unless `--no-builtin` is given,
so a scan with a bundle catches everything a scan without one does.

A bundle keeps its contents under a cipher, so that an antivirus does not
take it for the malware its rules describe.
[Rule files and your antivirus](#rule-files-and-your-antivirus) says what
that is about, and `--plain` builds a bundle without it.

### Other people's rules are not in this repository

Public rule sets belong to their authors and carry their own licences, some
of which restrict redistribution or commercial use. Warden therefore ships
none of them. The repository holds a pointer instead,
[`rules/yara-forge.pin`](../rules/yara-forge.pin): one release of
[YARA Forge](https://yarahq.github.io/), named by tag and SHA-256. YARA
Forge collects public rule repositories, filters them by quality, and
publishes the result as packages. Warden uses the "core" package, which
YARA Forge describes as leaving out rules that are prone to false positives
or slow.

```
scripts\win\check.cmd -Rules                                  (Windows: fetch, build and test)
bash scripts/fetch-rules.sh                                   (Linux)
warden rules build rules/vendor/yara-forge-rules-core.zip --exclusions rules/exclusions.toml --out rules/vendor/rules.wrb
```

The fetch scripts refuse a download that does not match the pinned
checksum. `warden rules info` lists the licences that the rules in a bundle
name, so you can see what you are running. For the pinned release, built
with the exclusion list described below:

| | |
|---|---|
| Release | 20261018 |
| Rules in the package | 5,137, all of which compile |
| Left out by the exclusion list | 6 |
| Rules in the bundle | 5,132: 5,131 from the package, plus the built-in rule |
| Repositories the package draws on | 35 |
| Rules that name a licence | 3,078 |
| Rules that name none | 2,054 |
| Reported as malicious (score 80 and above) | 205 |
| Reported as suspicious (score 60 to 79) | 3,305 |
| Generated by a tool: suspicious, and only together with a second sign | 1,622 |

### Rule files and your antivirus

A rule file is full of the byte patterns of the malware it describes; that
is what it is for. Microsoft Defender takes the YARA Forge package for the
real thing. On a Windows 11 desktop with real-time protection on, the
download was blocked the moment it was written, with the message "the file
contains a virus or potentially unwanted software". The hosted CI machines
run without real-time protection, so the package arrives there.

The remedy is the one used for the EICAR test folder: exclude one dedicated
folder, knowingly, and nothing more. That folder is `rules\vendor`. The
scripts keep the downloaded package and the bundle built from it there, so
one exclusion covers both, and the folder holds nothing else. From a
PowerShell window opened as administrator, in the repository:

```powershell
Add-MpPreference -ExclusionPath "$PWD\rules\vendor"
```

To undo it:

```powershell
Remove-MpPreference -ExclusionPath "$PWD\rules\vendor"
```

The scripts never do this for you. When the package is blocked, the Windows
fetch script says so and prints these two commands with the full path. With
the folder excluded, the download, the build of the bundle and a scan of
System32 with it ran through on the same machine.

Defender objects to compiled rules as well. A copy of a bundle that stored
its rules as they are, made outside that folder on the same desktop, was
blocked and then removed. A freshly installed Windows 11 without a network
did the same to such a bundle on the CD of the
[scan kit](TESTING.md#a-machine-the-list-was-not-written-from), and its
Defender gave the reason a name: `Trojan:JS/Webshell.DSK1!MTB`. Going by
the name, the patterns of rules that describe web shells are enough to be
taken for one. Warden got "the file contains a virus or potentially
unwanted software" when it opened the bundle, and the first scan there ran
without the public rules
([BENCHMARKS.md](BENCHMARKS.md#on-a-freshly-installed-windows-11)).

An exclusion is fine for development and not for a release: an installed
program cannot ask its users to exclude a folder. So a bundle keeps its
contents under a cipher, ChaCha20, with the key in the bundle's own header.
Warden takes the cipher off in memory when it opens the bundle, and
nothing is written back to disk without it. The quarantine keeps files the
same way and for the same reason
([QUARANTINE.md](QUARANTINE.md#what-the-cipher-is-for)).
[The format](#the-rule-bundle-format) has the layout, and what the cipher
is and is not good for.

What has been measured of this, on 2026-11-20 and the day after:

- **The patterns are gone from the file.** A bundle of 5,132 rules, one
  more than the table above has now, was built with the cipher and
  without. The one without holds 22,920 different stretches of eight or
  more printable characters, and none of them occurs in the other.
  Position by position, the two agree in one byte of 259, where chance
  would have one in 256.
- **Defender on the desktop left such a bundle alone for as long as it
  was watched.** The bundle with the cipher was put on that desktop
  outside the excluded folder, where the copy without the cipher had been
  blocked and removed, and copied once there. Nineteen and a half hours
  later both files were still there and read back with the checksum they
  had been written with. Real-time protection was recorded as on once in
  that time and not looked at otherwise. No bundle without the cipher was
  put next to them for comparison, because that would have raised an
  alarm on somebody's desktop on purpose.
- **The fresh Windows 11 blocked the bundle without the cipher and read
  the one with it, in one run.** That machine's Defender is the one that
  had named the plain bundle. The kit brought that very bundle again as a
  control, next to a bundle of the same compiled rules under the cipher.
  Defender blocked the control under the same name and has no entry for
  the other from that run, and Warden scanned the whole drive with it.
  Nothing on the machine had changed in between: it has no network, so
  its Defender and its signatures were the same, and real-time protection
  was on
  ([BENCHMARKS.md](BENCHMARKS.md#on-a-freshly-installed-windows-11)).

That is one antivirus with one set of signatures. What another product
does with a bundle, or this one after an update, is not known.

The figures and the times are in
[2026-11-20-dev-container-sealed-bundle.txt](benchmarks/2026-11-20-dev-container-sealed-bundle.txt).

One exclusion stays necessary on a Windows machine with Defender: the
rule package is a file of rule text, and building a bundle starts with
downloading it. A bundle that is already built has needed none so far:
the fresh Windows scanned with one from a CD, and on the desktop one lay
outside the excluded folder for most of a day.

## Rules that are left out

Public rules flag clean files now and then. With all 5,137 rules of the
pinned package, Warden reported 22 of 137,155 clean files in Windows system
folders and a CI runner's software as suspicious, and two rules accounted
for all 22. In the installed programs of a desktop, eight more rules
flagged 13 of 310,849 files ([BENCHMARKS.md](BENCHMARKS.md) has the runs).
A scanner that calls a system library suspicious teaches its user to ignore
it.

Four of those ten rules were generated by a tool. Rules of that kind are
dealt with as a kind, and those four are back in the bundle: see
[Generated rules](#generated-rules). The other six are left out. Which
rules, and on what evidence, is written down in one file:
[`rules/exclusions.toml`](../rules/exclusions.toml). A seventh rule was on
it for a day and is back in the bundle for another reason, see
[A rule that came off the list again](#a-rule-that-came-off-the-list-again).

They are of two kinds.

**Recognising a tool, not malware.** These four describe how a program was
packaged or protected. That is true of the files they flag, and it says
nothing against them.

| Rule | What it recognises | What it flagged |
|---|---|---|
| `COD3NYM_DOTNET_Singlefilehost_Bundled_App` | A way of packaging .NET programs. Its author gave it no score, the package fills in 75, and that makes every match suspicious | All 20 copies of `singlefilehost.exe` in the .NET SDK of a GitHub-hosted Windows runner |
| `DITEKSHEN_INDICATOR_TOOL_UAC_NSISUAC` | A plug-in of the NSIS installer builder | The uninstallers of two versions of FL Studio |
| `COD3NYM_SUSP_OBF_NET_Reactor_Indicators_Jan24` | .NET Reactor, a commercial obfuscator | Two files of a commercial .NET application; not named, see below |
| `CAPE_Obfuscar` | Obfuscar, an open-source obfuscator for .NET programs | A library of a small .NET utility; not named, see below |

**Asking for too little.** These two ask for a few common things and
little else.

| Rule | What it asks for | What it flagged |
|---|---|---|
| `SECUINFRA_SUSP_Powershell_Download_Temp_Rundll_1` | `$Env:temp`, `downloadfile(` and `rundll32.exe` anywhere in a file of any kind and size | `node_modules.asar` of Visual Studio Code, a 55 MB archive of JavaScript |
| `COD3NYM_SUSP_NET_Shellcode_Loader_Indicators_Jan24` | Three of six names of Windows memory and thread functions in a .NET program | `Clipchamp.Widgets.exe`, part of the video editor that Microsoft ships with Windows 11 |

### What an entry holds

```toml
[[rule]]
name = "COD3NYM_DOTNET_Singlefilehost_Bundled_App"
reason = "Recognises a way of packaging .NET programs, not malware. ..."
source = "cod3nym/detection-rules, through the YARA Forge core package 20261018"

[[rule.evidence]]
file = 'C:\Program Files\dotnet\packs\Microsoft.NETCore.App.Host.win-x64\10.0.14\runtimes\win-x64\native\singlefilehost.exe'
sha256 = "55b55ef1e98a4c4d1c8ef9d74042f69361a4bb5893ffd350f61042b59594ca8a"
seen = 2026-11-18
machine = "GitHub-hosted Windows runner (Windows Server 2025)"
```

The rule's name, the reason, and at least one piece of evidence: a clean
file the rule flagged, that file's SHA-256, the day, and the machine. An
entry without evidence is refused, and so is a field the format does not
know, so that a misspelt field is not skipped unnoticed. With the hash,
anyone who has the same file can repeat the observation.

There is one exception. The name and the hash of a file can give away
something private, such as which programs are installed on the machine of
the person who ran the scan. Evidence may then describe the file by its
kind and say why the rest is withheld:

```toml
[[rule.evidence]]
file = "the main program of a commercial .NET application protected with .NET Reactor"
withheld = "The name and the hash would show which programs are installed on a private machine."
seen = 2026-11-18
machine = "Windows 11 desktop"
```

One of `sha256` and `withheld` has to be there, and never both. Evidence
like this is weaker: nobody else can check it. Two entries rest on it
alone, the two obfuscator rules in the table above. What carries those
entries is the rule text, which anyone can read: each recognises a
protection tool that ordinary software uses, and says so in its
description.

### How a rule gets on the list

1. A false-positive run flags a file in a folder of clean software. The
   runs are described in [TESTING.md](TESTING.md).
2. Someone reads the rule and looks at the file: what the file is, where it
   came from, and what in it the rule matches.
3. `warden trust check` says who signed the file. If its publisher is one
   that belongs on the [trust list](TRUST.md#the-trust-list), that is the
   better remedy: it takes the match away from that publisher's files and
   leaves the rule in place for everything else. (The match in a file of a
   publisher that is on the list already gets this far only where the
   check does not reach: inside an archive, or when Windows could not find
   out whether a certificate was revoked.)
4. Otherwise, if the file is clean and the rule cannot tell it from its
   target, the rule gets an entry with the evidence.
5. The bundle is built again and the run repeated, and both results go into
   [BENCHMARKS.md](BENCHMARKS.md).

"Clean" rests on where the files were found. Those on the GitHub runner sat
in the Windows system folder and the .NET SDK folder of a machine image
that is built fresh from installers. `liblouis.dll` sat in the system
folder of a desktop in daily use with Microsoft Defender on. The files
from that desktop's installed programs belong to Git for Windows, Oracle's
Java runtime, Microsoft's Windows SDK, Visual Studio Code and Clipchamp,
and Image-Line's FL Studio, each in the folder its installer puts it in.
The six entries were made before Warden could check a signature, and who
signed their files was not part of the evidence. Step 3 is newer than they
are, and on 2026-11-25 it was done for the four named files that are on
the desktop. The two uninstallers are signed for Image Line. The archive
of Visual Studio Code is no executable and belongs to no package, so
there is no signature to look for. `Clipchamp.Widgets.exe` is covered by
the signature of its package, and the signer there is an identity of the
Microsoft Store for the app's publisher. None of the three is on the
trust list, so no entry could give way to it
([BENCHMARKS.md](BENCHMARKS.md#the-desktops-programs-with-the-rule-back-in-the-bundle)).
The three files of the CI runner were looked for on 2026-11-21, and the
runner no longer had them.

### What the build does with it

`warden rules build --exclusions rules/exclusions.toml` takes each listed
rule out of the rule text before it reaches the compiler. `warden-yara`
finds the rule with the parser that YARA-X itself uses and puts a stub of
the same name in its place, which the compiler discards. Everything else in
the file stays as it was, byte for byte.

- A rule is found by name, in every rule file that declares it.
- **Rules that use a listed rule are left out as well.** They cannot work
  without it. The build lists them among the rules that were left out, with
  the rule they depend on as the reason. No rule of the pinned package uses
  any of the six listed ones.
- **Some rules cannot be listed**, and the build stops if one is: the
  built-in rules, and `global` rules. A global rule narrows every other rule
  in its file, so without it all of those would match more than their
  authors meant.
- **A name that matches no rule is reported.** That brings a misspelt name
  to light, and an entry that a newer release of the rule set has made
  unnecessary.
- **The bundle records what happened**: the SHA-256 of the list it was
  built with, and the names of the rules that were taken out.
  `warden rules info` shows both, and a scan report counts the excluded
  rules next to the rules it used. The SHA-256 is that of the file, so
  `sha256sum rules/exclusions.toml` or `Get-FileHash` checks it.

### What it costs

A rule that is left out no longer finds what it was written for either.
Nothing else in the rule set recognises Obfuscar, and for .NET Reactor one
rule remains, which looks for another trace of it. That is the price of an
entry, and the reason the list asks for evidence instead of a feeling that
a rule is noisy.

How much detection the six entries cost is not measured. In every run so
far the six rules flagged clean files and nothing else, but no run held a
file they were written for.

The list also only knows what somebody has scanned. That is why it is the
tool for a rule that is wrong in a way of its own, and not for 1,622 rules
that are all made the same way.

### A rule that came off the list again

`RUSSIANPANDA_Purecrypter` was the seventh entry for one day. On 2026-11-20
the desktop's programs were scanned with administrator rights, which opens
the folder of the apps from the Microsoft Store, and one file of 310,910
was flagged: `xpdAgent.exe` of the Microsoft Defender app.

The rule shows how such a false positive comes about. PureCrypter is a
malware loader that is itself a .NET program. The rule asks for a program
under 6 MB with exactly one embedded resource, of more than 300 KB, and
for five sequences of instructions, four of which have to be there. Three
of them are creating an object, creating one and calling it, and the name
`ResourceManager`. The other two are runs of three and of five calls with
a generic method among them. A .NET program with one large resource of its
own can have enough of that without carrying anything, as `xpdAgent.exe`
shows, and the rule cannot tell the two apart.

So the rule went on the list, and the next scan flagged nothing. That
remedy took the rule away from every file on every machine, for the sake
of one file whose publisher is known: `xpdAgent.exe` carries a valid
signature of Microsoft Corporation. Since phase 5 Warden checks who signed
a file before it reports the match of a bundle's rule
([TRUST.md](TRUST.md)). A match in a file of a publisher on the trust list
is recorded and not reported, and the rule stays in the bundle for every
other file. On 2026-11-21 the entry was taken out again.

The scan that had put the rule on the list was repeated on 2026-11-25,
with administrator rights and the rule in the bundle. It matched
`xpdAgent.exe` again, the same file by its SHA-256. Warden found the
signature of Microsoft Corporation in it, the match went on record with
that reason, and none of 312,347 files was flagged
([BENCHMARKS.md](BENCHMARKS.md#the-desktops-programs-with-the-rule-back-in-the-bundle)).

## Generated rules

Of the 5,137 rules in the package, 1,622 were not written by a person. They
come from [Malpedia](https://malpedia.caad.fkie.fraunhofer.de/), a
collection of malware samples sorted by family, and are made by a tool,
[YARA-Signator](https://github.com/fxb-cocacoding/yara-signator). For each
family it picks sequences of machine code that set the family's samples
apart from the other families in the collection, usually ten of them. All
but one of the 1,622 rules ask for seven of their sequences. Each rule says
where it comes from, in its metadata:

```
description = "autogenerated rule brought to you by yara-signator"
tool = "yara-signator v0.6.0"
score = 75
```

Such a rule is good at telling its family from the other families in the
collection. It is less good at telling it from the rest of the world. If
the samples carry a common library, some of the sequences are that
library's, and any program built with the same library can have them. Four
of these rules, each with ten sequences, flagged clean files in the first
runs:

| Rule | Clean files it matches |
|---|---|
| `MALPEDIA_Win_Triback_Loader_Auto` | `vulkan-1.dll` in System32 of a GitHub-hosted Windows runner, and `liblouis.dll`, a braille library, in System32 of a Windows 11 desktop |
| `MALPEDIA_Win_Bqtlock_Auto` | `libstdc++-6.dll`, the GNU C++ runtime library, in Git for Windows (two copies) |
| `MALPEDIA_Win_Mystic_Stealer_Auto` | `zip.dll` and `unpack200.exe` of the Java runtime. At least three of the rule's sequences are zlib's compression code |
| `MALPEDIA_Win_Yokai_Auto` | `ucrtbased.dll`, the debug build of Microsoft's C runtime, in two places of the Windows SDK |

Until phase 4 these four were on the exclusion list. A list cannot keep up
with this: it knows what somebody has scanned, and every machine with other
software on it is likely to meet the next rule of the 1,622.

### What a match of a generated rule means

It is a reason to look at the file, and not yet a finding. So it **counts
only together with a second sign**.

- The YARA layer recognises a generated rule by its `tool` field, which
  starts with `yara-signator`. Whatever score the rule states, its match is
  never rated higher than medium: it can make a file suspicious and never
  malicious.
- Its finding is marked as one that needs backing. The verdict policy lets
  it count when another layer has something to say about the same file,
  and otherwise keeps it on record with the verdict it would have had
  without it.
- Today the other layer is the heuristic one. It reports a file as
  suspicious from a score of 32. From a score of 14 it reports the file as
  unusual, which is a second sign and nothing more.
  [HEURISTICS.md](HEURISTICS.md#the-bar-for-a-second-sign) has where 14
  comes from. A hash match would do as well, and makes the file malicious
  on its own anyway.
- A layer does not back itself. Two generated rules matching one file are
  one layer saying the same thing twice.
- Inside an archive each member is settled by itself: a rule match in one
  member and an odd structure in another do not add up.

A file whose finding did not count has the verdict "clean". The scan
report keeps the finding all the same, in a list of its own, so that the
reason a file was not reported can be looked up. This is what a scan
prints for two inert files of the test suite and a test rule that says a
tool made it and matches both (the paths are cut down to the file names).
The first file is built like an ordinary program; the second looks packed,
which the heuristic layer scores at 28:

```
  ON RECORD   Test_Generated_Starts_Like_A_Program
    b-plain.exe
    sha256 605b438d1627f2498515cd2ff69855e1ccf00b461e0d1afed27fad4bebc53b9c (24,064 bytes)
    yara [malware]: YARA rule Test_Generated_Starts_Like_A_Program matched: autogenerated rule brought to you by yara-signator
    yara [malware]: Rule score 75 of 100
    yara [malware]: The rule was generated by a tool, yara-signator v0.6.0, from samples of one malware family. Such a rule also matches code that those samples share with clean software, so its match counts only together with a sign from another layer
    yara [malware]: No other layer has anything to say about this file, so this is recorded and does not change the verdict

  SUSPICIOUS  Test_Generated_Starts_Like_A_Program, Heuristic.UnusualExecutable
    c-packed-looking.exe
    sha256 633fb8b51ed6c20ae620d40d94765f72371112717ed0783644a8991923bff04d (17,408 bytes)
    yara [malware]: YARA rule Test_Generated_Starts_Like_A_Program matched: autogenerated rule brought to you by yara-signator
    yara [malware]: Rule score 75 of 100
    yara [malware]: The rule was generated by a tool, yara-signator v0.6.0, from samples of one malware family. Such a rule also matches code that those samples share with clean software, so its match counts only together with a sign from another layer
    yara [malware]: Counts, because another layer has something to say about the same file: heuristic
    heuristic [malware]: The structure of the file scores 28: less than the 32 that make a file suspicious, and at least the 14 from which it backs up a finding of another layer
    heuristic [malware]: +10 A section is both writable and executable: sections "UPX0", "UPX1"
    heuristic [malware]: +9 An executable section looks compressed or encrypted: section "UPX1" has an entropy of 7.99 bits per byte
    heuristic [malware]: +5 The header holds no checksum: the checksum field is zero
    heuristic [malware]: +4 The program has no resources: the header points to no resource table
```

Without the rule, the second file is not reported either: a score of 28 is
below the 32 from which the heuristic layer speaks on its own. Neither
layer alone has enough, and together they do.

### What the four rules do now

They are in the bundle again, and every false-positive run was repeated
with them
([BENCHMARKS.md](BENCHMARKS.md#with-a-second-sign-for-generated-rules) has
the numbers).

| File | Before | Now |
|---|---|---|
| `vulkan-1.dll` on the CI runner | Suspicious | Verdict clean, the match on record |
| `liblouis.dll` in System32 of the desktop | Suspicious | The same |
| `libstdc++-6.dll` (two copies), `zip.dll`, `unpack200.exe` and `ucrtbased.dll` (two copies) among the desktop's programs | Suspicious | The same, all six |

Each of the eight files had the SHA-256 it had when it was flagged. No
file was flagged in these runs.

**The Triback rule also showed what a list cannot do.** It went onto the
exclusion list after the first round, before the programs of the desktop
were scanned for the first time, so it had never run over them. Back in
the bundle, it matched four more clean libraries there: `SDL3_image.dll`,
`libavif-16.dll` and `libpng16-16.dll` of Steam, and
`driver_VirtualDesktop.dll` of Virtual Desktop Streamer. No list had these
files. The heuristic layer has nothing to say about any of them, so all
four are on record with the verdict clean, and nothing had to be written
down for that to happen.

It happened twice more. Scanned with administrator rights, the desktop's
programs include the apps from the Microsoft Store, which the run before
could not list, and the rule matched four clean files there:
`NativeHostNE.dll` of Phone Link, and `pyshellext.exe`, `launcher-64.exe`
and `launcherw-64.exe` of the Python install manager. And on the Windows
11 that was installed for the test, a machine no list was written from,
it matched five: `vulkan-1.dll`, which is the runner's file, `liblouis.dll`
in another build than the desktop's, and `NativeDprt.dll` of Defender's
own sensor, the last two each with a copy in the component store. All
nine are on record too. That made fifteen clean files for this one rule,
on three machines, and none of them reported. A run in phase 5 added two
on the CI runner, `node_js2c.exe` and `nop.exe` in a tool pack of .NET
that the runner's image had gained since: seventeen.

### What the second sign costs

A generated rule that matches real malware with a plain-looking structure
no longer reports it. How often that happens cannot be measured here,
because it takes malware samples, and this project does not handle any.
What can be said comes from the EMBER2024 dataset: of its malicious
programs, a little more than half have a structure that scores 14 or more
(55% in the training weeks, 56% in the test weeks), and of its malicious
libraries about three in ten. For the rest, a generated rule would be the
only layer speaking, and it now speaks on record only. That is a real
loss, stated here as a limit. For three of the four families in the table
above, the generated rule is the only rule of the set that names the
family; for Mystic Stealer two hand-written rules remain.

The other 3,510 rules of the bundle are not affected: a rule that a person
wrote still counts alone.

## From a match to a verdict

Detectors report, a policy decides: that rule of the engine holds here too.

1. A rule states how much a match means with a `score` from 0 to 100 in its
   metadata. This is a convention of public rule sets, described in the
   [YARA Style Guide](https://github.com/Neo23x0/YARA-Style-Guide): 80 to
   100 for direct matches on malware and hack tools, 60 to 79 for
   heuristics and generic detections, lower for things that are only
   noteworthy.
2. The YARA layer turns the score into a confidence: 80 and above is high,
   60 to 79 is medium, anything lower is low. A rule without a score is
   treated as 75.
3. A rule that a tool generated is the exception: its match is rated
   medium at most and counts only together with a second sign, see
   [Generated rules](#generated-rules).
4. The engine's verdict policy first settles which findings count, and
   then turns the strongest confidence among them into a verdict: high is
   malicious, medium is suspicious, low changes nothing.

So a single match of a generic rule that a person wrote makes a file
suspicious, which is shown to the user and never acted on automatically.
Only rules whose authors rate them as direct matches make a file
malicious. The thresholds are options (`YaraOptions`), not constants.

Metadata that Warden reads from a rule:

| Field | Use |
|---|---|
| `score` | Confidence, as above |
| `threat_name` | The name the detection is reported under. Default: the rule's name |
| `category` | `malware` (default), `test_file` or `potentially_unwanted` |
| `description`, `author`, `reference` | Shown as the reasons for a detection |
| `tool` | A value that starts with `yara-signator` marks the rule as generated |
| `license`, `license_url` | Listed by `warden rules info` |

A detection always says why. These are the lines the built-in rule
produces for the test file:

```
yara [test file]: YARA rule Warden_EICAR_Test_File matched: the EICAR antivirus test file, a harmless file that every scanner detects on purpose
yara [test file]: Patterns found: $first at offset 0x0, $second at offset 0x21
yara [test file]: Rule score 100 of 100, written by Vevang Technologies, see https://www.eicar.org/download-anti-malware-testfile/
```

When many rules match one file, the ten with the highest scores are listed
and the rest are counted.

## Limits

- **Time.** One file may take the rules 30 seconds. After that the scan of
  that file is given up and the file is listed as partially scanned, with
  the reason `timeout`.
- **Size.** Files larger than the content limit (128 MiB by default) are
  checked by hash only and listed as partially scanned, with the reason
  `too_large`.
- **Modules.** The build includes the YARA modules `pe`, `dotnet`, `elf`,
  `macho`, `lnk`, `hash`, `math`, `string`, `time` and `console`. Rules
  that need another module (`magic`, `cuckoo` and a few more) are left out
  of the bundle and counted.
- **Includes.** An `include` statement in a rule file is a compile error.
  The included file would be missing from the bundle's record of where its
  rules came from, and the exclusion list would not see the rules in it.
  Give the builder every rule file directly, or a folder of them.
- **One thread, one scanner.** A YARA-X scanner holds the state of the rule
  engine and cannot be shared. Each worker thread has its own; the compiled
  rules are shared.
- **Packed and encrypted content.** Rules see the bytes of a file as it is
  on disk. Warden unpacks zip archives and runs the rules over the members;
  it does not unpack executables that are packed or encrypted. That is what
  the next layer, PE heuristics, is for.

## The rule bundle format

A bundle (`.wrb`) is one file: a fixed header, a manifest that records
where the rules came from, and the compiled rules. All integers are
little-endian.

There are two versions. Version 2 keeps the manifest and the rules under a
cipher, and is what `warden rules build` writes. Version 1 stores them as
they are; `warden rules build --plain` writes it. Warden reads both, and
`warden rules info` says which of the two a file is.

| Offset | Size | Field |
|---|---|---|
| 0 | 8 | Signature: `WRDNRUL` followed by a zero byte |
| 8 | 4 | Format version: 1 or 2 |
| 12 | 4 | Header length: 96 in version 1, 128 in version 2 |
| 16 | 4 | Flags: 0 |
| 20 | 4 | Number of rules |
| 24 | 8 | Creation time, seconds since the Unix epoch |
| 32 | 8 | Length of the manifest in bytes |
| 40 | 8 | Length of the compiled rules in bytes |
| 48 | 16 | Reserved: zero |
| 64 | 32 | Digest: SHA-256 of the whole file apart from these 32 bytes |
| 96 | 32 | Version 2 only. Key: SHA-256 of the manifest followed by the compiled rules, as they are without the cipher |

The manifest follows the header, and the compiled rules follow the
manifest, in the form YARA-X serialises them. In version 2 the two together
are under ChaCha20 as [RFC 8439](https://www.rfc-editor.org/rfc/rfc8439)
defines it: the key from the header, a nonce of twelve zero bytes, and a
block counter that starts at zero. The two lengths in the header are the
same in both versions, because a stream cipher leaves the length of what it
is applied to as it was.

The manifest is UTF-8 JSON:

```json
{
  "engine": "yara-x 1.23.0",
  "sources": [
    {
      "name": "warden/builtin.yar",
      "sha256": "e157092d259c6412922c8fae43f4b90d47d426045d2b7ea1ce76e8002ec51cee",
      "bytes": 1844,
      "rules": 1,
      "skipped": 0
    },
    {
      "name": "yara-forge-rules-core.zip/packages/core/yara-rules-core.yar",
      "sha256": "7770d912c4b1f7ce67d3614abda9a96d9d9dd2b5207b30ae0b4e7ba96bbdb0f8",
      "bytes": 7879714,
      "rules": 5131,
      "skipped": 0,
      "excluded": 6
    }
  ],
  "exclusions": {
    "sha256": "the SHA-256 of the exclusion list",
    "rules": [
      "CAPE_Obfuscar",
      "COD3NYM_DOTNET_Singlefilehost_Bundled_App",
      "...four more"
    ]
  }
}
```

`sha256` and `bytes` of a rule file describe the file as it was given to the
builder, before listed rules were taken out. `excluded` is written only when
it is not zero, and `exclusions` only when the bundle was built with an
exclusion list. Both were added after version 1 was first written down. A
reader that does not know them ignores them, and a bundle without them
loads as before, so the version number did not change.

When a bundle is opened, Warden checks in this order: the signature and
the version, that the header length is the one of that version, that the
three lengths add up to the size of the file, the digest, in version 2 that
the key is the SHA-256 of what it opens, the manifest, that the bundle was
built with the same YARA-X release as the program, and that the number of
rules matches the header. A file that fails any check is refused as a whole.

Compiled rules load only in the YARA-X release that compiled them. A bundle
from another release is refused with the advice to build it again; the rule
files themselves stay valid.

### What the cipher is for, and what it is not

The cipher keeps the bundle from being taken for the malware its rules
describe ([Rule files and your antivirus](#rule-files-and-your-antivirus)).
It keeps nothing secret. The key is in the header, how to use it is
written down above, and `warden rules build --plain` writes the same rules
without it.

The key is made from the contents, where the quarantine draws a random key
for every entry. A bundle is something that is built, and the same rules
should give the same file. They do: two runs of `warden rules build` with
the same rule package, exclusion list and creation time wrote the same
file byte for byte, with the cipher and without it. Without it, a build on
Linux also gave the very file that the Windows build of the day before had
written on the desktop, once it was given the exclusion list and the
creation time of that file. A key made from the contents needs no source
of random numbers either. And it is why the nonce can be zero: a nonce
keeps one key from making the same stream for two texts, and here a key
only ever belongs to one.

What the cipher costs is time at every start, when the contents are
copied, opened and checked against the key. For the bundle of 5,132 rules
(8.7 MB) those three steps take 9 ms in the development container, where
a start with this bundle takes half a second
([BENCHMARKS.md](BENCHMARKS.md#what-the-cipher-on-the-rule-bundle-costs)).

It does not hide the patterns from a program that reads the memory of
others. That is no different from any other program that scans with YARA
rules, and Defender, which removed the file without the cipher, did not
object to Warden while it scanned the desktop with those rules loaded.

### What the digest does and does not protect

The digest catches damage: a truncated download, a flipped bit. It does not
authenticate the bundle. Someone who can replace the file can write a
matching digest, and YARA-X's own documentation warns against loading
compiled rules from a source that is not trusted.

A bundle is therefore trusted in the same way as the program itself: it
must come from a place that only trusted users can write to. For the
command-line tool that is your own folder. For the service planned in phase
6 it is a folder that only the service and administrators can write to, and
phase 11 adds a signed manifest that covers the program, the signature
database and the rule bundle together.
