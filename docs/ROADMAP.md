# Roadmap

Warden is built in phases. Each phase ends with something that can be run
and tested, and no phase starts before the previous one is accepted.

| # | Phase | Ends with | Status |
|---|---|---|---|

| 2 | YARA layer + zip scanning | The same command catches an EICAR variant whose hash is not in the database, and EICAR inside a zip; the rule bundle builds from YARA Forge; first false-positive run over System32 | Done, accepted 2026-11-18 |
| 3 | PE heuristics | `warden inspect <file>` explains a score indicator by indicator; calibration report against EMBER2024; fuzzers running | Done, accepted 2026-11-18 |

Phases 1 to 8 deliver every portfolio deliverable. Phases 9 to 11 add the
systems depth.

## Phase 4, first half: a second sign for generated rules

**What.** Of the 5,137 rules in the rule package, 1,622 are generated by a
tool from the samples of one malware family each. Until phase 4 a single
match of one of them made a file suspicious. Now such a match is recorded
and changes nothing on its own; it makes a file suspicious when another
layer has something to say about the same file, which today means a
heuristic score of 14 or more. [RULES.md](RULES.md#generated-rules) has
how it works, and [HEURISTICS.md](HEURISTICS.md#the-bar-for-a-second-sign)
where the 14 comes from.

**Why.** Four of those rules had flagged clean files, in about 448,000
files on two machines: the Vulkan loader, a braille library, the GNU C++
runtime, zlib inside Java, and Microsoft's debug C runtime. The likely
reason is the same each time, and for one of the four it can be read in the
rule: the samples and the clean file share library code. The exclusion
list takes such a rule out after somebody has met it, and every machine
with other software on it is likely to meet another one.

**What it took.**

- The YARA layer recognises a generated rule by the `tool` field of its
  metadata, when it reports a match. The plan was to record it in the rule
  bundle; that turned out not to be needed, so the bundle format did not
  change for it.
- The heuristic layer reports a score below its threshold too, from a
  lower bar on, as something to count with and not as a finding. That
  brought back the lower level that phase 3 removed because nothing used
  it.
- The verdict policy settles which findings count before the strongest
  one decides.
- A scan report keeps what was recorded without a verdict, so that the
  reason a file was not flagged can be looked up.

**Why in phase 4, and first.** It changes what a verdict is and what a
report holds. From phase 4 on, verdicts lead to actions; phases 6 and 7,
the service and the desktop app, read reports. The change was cheapest
before any of them existed.

**Done when.** The false-positive runs on the CI runner and on the desktop
are repeated with the four generated rules put back into the bundle, and
the clean files they flagged are no longer reported. An inert test file
that a generated test rule matches is reported when its structure is
suspicious too, and not when it is plain.

**Where that stands.**

| | |
|---|---|
| The test with inert files | Done, in the test suite |
| The CI runner | Done: no file flagged in 109,513, and `vulkan-1.dll`, which a generated rule flagged in the first round, is on record with a clean verdict |
| The desktop | Done: no file flagged in 285,917. The seven files that the four rules flagged there are on record with a clean verdict, and so are four clean libraries that nobody knew of: the rule that matches them had been on the exclusion list since before those folders were first scanned |

**Beyond the criterion.** A Windows 11 was installed in a virtual machine
for runs on files that nothing here was written from. Its Defender
blocked the rule bundle, so the first run was without the public rules:
none of 153,317 files flagged. For that reason a bundle now keeps its
contents under a cipher
([RULES.md](RULES.md#rule-files-and-your-antivirus)). With such a bundle
the run was repeated with all 5,132 rules: none of 153,370 files flagged,
and five on record with a clean verdict. The kit carried the old bundle
along for comparison, and Defender blocked it again
([BENCHMARKS.md](BENCHMARKS.md#on-a-freshly-installed-windows-11)).

The desktop's programs were also scanned once more, with administrator
rights, which open the folder of the apps from the Microsoft Store. One
file of 310,910 was flagged there: a clean one, by a rule that was written
by hand. The four generated rules flagged nothing, and four more of their
matches are on record. The hand-written rule went on the exclusion list as
its seventh entry, and the repeat with that list flagged none of 311,415
files
([BENCHMARKS.md](BENCHMARKS.md#the-desktops-programs-again-with-administrator-rights)).

**What it cannot show.** What the change costs in detection. A generated
rule that matches plain-looking malware no longer flags it alone, and
without malware samples, which this project does not handle, that cost
cannot be measured. It is stated as a limit.

The exclusion list stays, with seven entries by the end of the phase. It
is still the right tool for a rule that is wrong in a way of its own, such
as one that recognises an installer plug-in. The seventh entry was not of
that kind, and phase 5 took it off again.

## Phase 5, first piece: a signature-trust check

**What.** Warden learns to check who signed a file. A signature can be in
three places: inside the file; in a catalogue that Windows keeps for its
own files; or, for an app from the Microsoft Store, in the signature of
the app's package. The check tries all three and compares the signer with
a short list of trusted publishers that is part of the program. A match of
a published rule on a file with such a signature is kept on record and
does not change the verdict.

**Why.** Scanned with administrator rights, the desktop's programs held
`xpdAgent.exe` of the Microsoft Defender app, and a rule written by hand
flagged it. Windows reports a valid signature of Microsoft Corporation for
that file. Warden could not see it: all it knew of a signature was whether
one is there. So the rule went onto the exclusion list, and there it finds
nothing any more, on any file. That list is for a rule that is wrong. This
rule may be right about what it looks for; what settles the matter is who
the file comes from. One route is not enough either: 77 % of the
executables in System32 carry no signature of their own
([HEURISTICS.md](HEURISTICS.md#the-signature)).

**What it takes.**

- **Three routes.** An embedded signature is checked by Windows itself.
  For the Windows catalog, the file's hash is looked up in the catalogues
  Windows has installed, and the catalogue's signature is checked. For a
  package, Warden hashes the file in blocks and compares them with the
  package's block map, compares the block map with the digest in the
  package's signature, and has Windows check that signature.
- **The same bytes.** The check holds the file open so that nobody can
  change it meanwhile, and compares its SHA-256 with the one the scan
  computed. Its answer is about the bytes that were scanned.
- **A list, and a narrow one.** A valid signature is not trust: malware is
  signed too, with certificates that were bought or stolen. The list names
  signing identities, each with the certificate it must chain to and the
  evidence it was added on, and it starts with two: Microsoft Corporation,
  and Microsoft Windows, which signs the catalogues of Windows itself.
  How a publisher gets on the list is written down with it.
- **Revocation.** Windows is asked whether a certificate in the chain has
  been revoked. A signature whose revocation cannot be checked, on a
  machine without a network for one, does not count as trusted.
- **Only when it matters.** The check is asked for a file only when a
  finding would otherwise be reported that a signature can hold back.
  That keeps a scan as fast as it is.
- **What yields and what does not.** A match of a rule that came with a
  rule bundle yields. A hash match is always reported. So is a match of
  one of Warden's own built-in rules, and so is what the heuristics say:
  the decision was made for published rules, and nothing else has been
  measured to need it.
- **Something to run.** `warden trust check <file>` explains what each
  route found, who signed, what the chain ends in and whether that is on
  the list. `warden trust list` prints the list with its evidence, and
  `warden trust survey <folder>` counts routes and signers, for the
  measurements.

**Done when.**

1. `warden trust check` gives the right answer in CI on Windows: for files
   that are signed there for the test, valid, changed after signing, with
   bytes added to the signature area, by a publisher that is not on the
   list and with a certificate whose revocation cannot be checked; for a
   package made there; and for files of Windows itself.
2. It is measured, on the CI runner and on the desktop: how many files
   each route covers, who signs them, and what a check costs.
3. `RUSSIANPANDA_Purecrypter` is off the exclusion list again, and the
   scan of the desktop's programs with administrator rights flags no file
   with that rule in the bundle. `xpdAgent.exe` is on record with the
   reason.

**Where that stands.**

| | |
|---|---|
| 1. The right answers in CI on Windows | Done. The Windows job makes the signatures and asks the real Windows about them, and 463 tests pass there. Windows' own tool calls two of the test files valid that Warden turns down: one with bytes added next to its signature, and one signed for "Microsoft Corporation" under a root made for the test ([BENCHMARKS.md](BENCHMARKS.md#signatures-made-to-be-turned-down)) |
| 2. Measured on the CI runner | Done. Of the 8,760 executables in System32, 97.5 % are trusted: 19 % by the signature in the file and 78 % through a catalogue. In the folder of the app packages all 1,054 executables are, 414 of them through their package. A check takes 4 to 8 ms at the median, and 154 ms through a catalogue on a machine that is asked for the first time ([BENCHMARKS.md](BENCHMARKS.md#who-signed-what)) |
| 2. Measured on the desktop | Done, on 2026-11-25. In System32, 94.7 % of 12,132 executables are trusted, 78 % through a catalogue. In the folder of the app packages 99.6 % of 20,205 are. The 13,440 other files there that belong to other publishers' apps are not, although nearly all of them are signed under a root of Microsoft's ([BENCHMARKS.md](BENCHMARKS.md#on-the-desktop)) |
| 3. The rule off the list, and the desktop's scan clean | Done, on 2026-11-25. With `RUSSIANPANDA_Purecrypter` in the bundle and administrator rights, the scan of the desktop's programs flags none of 312,347 files. The rule matches `xpdAgent.exe` as before; the match is on record with the reason that Microsoft Corporation signed the file ([BENCHMARKS.md](BENCHMARKS.md#the-desktops-programs-with-the-rule-back-in-the-bundle)) |

The first piece met its three criteria on 2026-11-25. Before the second
piece, phase 5 got one more thing, decided that day: a guard that keeps a
file that Windows itself signed out of the quarantine. It is built.
`warden quarantine add` leaves such a file where it is and says why, and
`--even-if-signed-by-windows` takes it all the same
([QUARANTINE.md](QUARANTINE.md#the-guard)). In CI on Windows it does so
with copies of `ntdll.dll`, which carries its signature, and of
`whoami.exe`, which a catalogue lists; 482 tests pass there.

**What it cannot show.** That a publisher on the list still holds its key:
revocation helps only once a theft is known. Nothing about a file inside
an archive, which has no place on disk to check. And, as with the second
sign, what the change costs in detection: a published rule no longer flags
a file that carries a trusted signature, and without malware samples that
cost cannot be measured.

The second piece of the phase, persistence remediation, follows it.

## Phase 5, second piece: persistence remediation

**What.** A program that wants to stay makes Windows start it again: with
a value under a Run key, a scheduled task, a service, or a shortcut in the
Startup folder. Taking the file away leaves those entries pointing at
nothing. This piece finds the entries that start a file, removes them when
the file goes into the quarantine, and puts them back when it is restored,
each as it was.

**Why.** An entry that starts a quarantined file is a loose end. Windows
reports an error at every start, or something else is put at that path and
gets started. And a restore that brings back the file without what started
it has not undone the quarantine. The rule is the quarantine's own: nothing
is destroyed, and what is taken can be put back exactly.

**What it takes.**

- **Four places.** Run and RunOnce values, of the machine and of every user
  whose settings are loaded; scheduled tasks; services and drivers, by
  their program and by the library that a shared service host loads for
  them; shortcuts in the two Startup folders. Windows has many more places
  that start programs. The document lists what is covered and what is not.
- **What "starts the file" means.** The file's full path stands in the
  entry's command line, as the program or as an argument, once the
  variables in it are filled in. `rundll32 C:\x\a.dll,Start` starts
  `a.dll`. A bare name that Windows would look for on its search path is
  not followed.
- **Windows is asked where Windows owns the format.** Tasks are read,
  removed and registered through the Task Scheduler, shortcuts are read
  through the shell, services through the service manager. Warden does not
  edit their files or their registry keys behind their back.
- **Record first, then remove.** Everything an entry is goes into a record
  in the quarantine before the entry is touched: a value with its type and
  its bytes; a task as the definition the Task Scheduler gives for it,
  with its access rights; a service with its configuration, its registry
  key and its access rights. A shortcut is a file and goes into the
  quarantine as one. An operation that is cut off is finished or undone
  the next time the quarantine is opened, as it is for files.
- **A restore looks before it writes.** An entry that is there already and
  the same is left. One that is there and differs is not replaced, and the
  restore says so. Afterwards the entry is read back and compared with the
  record; a difference is reported.
- **Only for a file that is in the quarantine, and never for a file of
  Windows.** Entries are removed once the file is safe in the quarantine,
  not before. A file that was taken past the guard keeps its entries: a
  program of Windows can have services of Windows that start it.
- **Rights.** The machine's entries need administrator rights. Without
  them, what belongs to the user is removed and the rest is named.
- **Something to run.** `warden autostart find <file>` shows what starts a
  file and changes nothing. `warden autostart list` shows every entry
  Warden looks at.
- **One more library.** Tasks and shortcuts are COM interfaces. Microsoft's
  `windows` crate has them; `windows-sys`, which the project uses
  elsewhere, leaves COM out by design. The crate is used in one module,
  on Windows only.

**Done when.**

1. In CI on Windows, with a harmless dummy program and the four entries
   made with Windows' own tools: `warden autostart find` names all four;
   `warden quarantine add` removes the file and all four, as Windows' own
   tools then show; `warden quarantine restore` brings the file and all
   four back, and each is what Windows' tools showed before.
2. The same in the virtual machine, from a kit, with the dummy registered
   as a test threat that a scan reports. The result is in the repository.
3. Cut off after every step, an operation leaves every entry either in
   its place or in the record, whole.

**What it cannot show.** That the persistence of real malware is found:
the dummy uses the four places from the textbook, and nothing here is
tested against a sample.

## Decisions

| Date | Decision |
|---|---|
| 2026-11-18 | Name: Warden. Engine and core logic in Rust; desktop app in Tauri with React and TypeScript. |
| 2026-11-18 | Detection layers in order: hash matching, YARA rules, PE heuristics, then an optional ML classifier. |
| 2026-11-18 | No live malware, ever: not written, generated, modified or handled. Tests use the EICAR file, inert fixtures and public feature data. Detection rates on live samples are therefore reported as not measured, and the README says why. |
| 2026-11-18 | In scope beyond the original brief: zip scanning with limits on nesting depth, unpacked size, member count and compression ratio (phase 2); scheduled scans (phases 6 and 7); ClamAV as a benchmark reference (phase 8); an alert on new autostart entries (phase 9); an AMSI provider as the last optional phase. |
| 2026-11-18 | The repository is private until the portfolio checkpoint (phase 8). |
| 2026-11-18 | Real-time protection starts in user mode. A kernel minifilter is a late, optional, VM-only phase, because distributing a driver needs Microsoft's signature. |
| 2026-11-18 | The rule engine is YARA-X, VirusTotal's rewrite of YARA in Rust. It needs no C toolchain, which keeps the Windows build to `cargo build`, and the original YARA has been in maintenance mode since YARA-X 1.0 came out in June 2025. |
| 2026-11-18 | Third-party rules are not stored in this repository. A script downloads one pinned YARA Forge release and checks its SHA-256; `warden rules build` compiles it into a bundle. The rules keep their authors' licences. Warden itself ships one rule, for the EICAR test file. |
| 2026-11-18 | A rule's `score` decides the verdict: 80 and above is malicious, 60 to 79 suspicious, below 60 recorded only. A rule without a score counts as 75. The ranges are those of the YARA style guide that YARA Forge follows. |
| 2026-11-18 | Zip archives are unpacked in memory, never to disk, with limits on depth (3), members (10,000), member size (64 MiB), total size (512 MiB) and compression ratio (250 to 1). Reaching a limit is reported per file; it is not a detection. |
| 2026-11-18 | A public rule that flags clean files is left out of the rule bundle. The rules that are left out are listed in one file in the repository, `rules/exclusions.toml`, and every entry needs evidence: the clean file, its SHA-256, the day and the machine. The bundle records which list it was built with. This settles what to do about the two rules that flagged 22 clean Windows files in the first false-positive runs. The alternative, letting the verdict policy ask for a second sign before a medium-score match alone makes a file suspicious, was not chosen; it can be looked at again when the heuristic layer exists. |
| 2026-11-18 | Rule files may not `include` other files. A bundle records every rule file it was built from, and an included file would be missing from that record and invisible to the exclusion list. |
| 2026-11-18 | The heuristic layer reads Windows executables with a reader of its own. It keeps going where a general-purpose parser gives up, because a damaged header is a finding here; and it collects exactly the facts that EMBER2024 records, so that indicators can be measured on the dataset. It is checked against the `object` crate, which is a test dependency only. |
| 2026-11-18 | The weight of a heuristic indicator is fitted to EMBER2024, not chosen: a logistic regression over all indicators together, with the kind of file (program, library, .NET assembly) as a term of its own, no negative weights, and nothing below 3 decibans. The threshold is the lowest score that at most one in 5,000 benign training files of any kind reaches. The counts the fit rests on are in the repository, and a test fails if the scanner's numbers are not what they give. Measuring each indicator on its own was tried first and rejected: it mistakes "is a program" for evidence and counts "is packed" several times. |
| 2026-11-18 | The heuristic layer reports a file as suspicious at most, never as malicious, and has one threshold. A second, lower level that changed nothing in a scan was removed. |
| 2026-11-18 | Whether a file has an embedded signature is not scored. Presence says nothing about validity, and under the same rule for the threshold the score flags more malicious files of the test weeks without it than with it. |
| 2026-11-18 | Eight more rules are on the exclusion list, after they flagged 13 of 310,849 files among the installed programs of a desktop. The heuristic layer flagged none of those files. |
| 2026-11-18 | Evidence on the exclusion list may withhold the name and the hash of a file, with a stated reason, where they would show which programs are installed on a private machine. Two entries rest on such evidence. The price is that nobody else can check it, and the list says so. |
| 2026-11-18 | The second sign for generated rules, set aside when the exclusion list was chosen, is now scheduled as the first piece of phase 4. A list that only knows what somebody has scanned does not scale to 1,622 generated rules. |
| 2026-11-18 | A structure counts as a second sign from the lowest score that at most one in twenty benign training files of every kind reaches. That is 14. One in twenty is a choice: reaching the bar reports nothing, so it can be far looser than the threshold's one in 5,000. |
| 2026-11-18 | The four generated rules come off the exclusion list. The list keeps the six rules that are wrong for a reason of their own. |
| 2026-11-18 | `warden.exe` is linked with the C runtime inside. The build before asked for `vcruntime140.dll`, which is on most Windows machines and not guaranteed on a fresh one. The price is a larger program, with a C runtime in it that Windows Update does not replace. |
| 2026-11-18 | The quarantine keeps the content of a file under ChaCha20 with the key next to it. The purpose is to make the bytes on disk useless as a program and invisible to other scanners, not to keep them secret from the user who owns the quarantine. |
| 2026-11-18 | An interrupted quarantine operation is settled when the quarantine is next opened: undone if the copy had not reached its destination, finished if it had. Finishing is the right default for a file somebody asked to have out of the way. |
| 2026-11-19 | On Windows, the read-only bit and the security descriptor of a restored file are put back after the file has its name, through the handle the file was written with. Before, they can stop the restore itself. |
| 2026-11-18 | The quarantine belongs to the user who runs Warden until there is a service. A quarantine for the whole machine needs a program with rights of its own, and that program must not restore to places its user could not write to. |
| 2026-11-20 | The kit for a fresh machine does not stop when that machine's antivirus blocks the rule bundle. It says so and scans with the layers that need no bundle. It changes no antivirus setting, like every script here. |
| 2026-11-20 | A command whose output nobody reads any more, as when it is piped into `head`, stops quietly with exit code 2. It used to end in a panic. Everything the command-line program prints goes through one place that can fail, and a lint keeps out the printing macros that cannot. |
| 2026-11-20 | A scan counts the folders it could not open apart from the files it could not read, and a false-positive result names them. An unreadable folder used to count as one skipped entry, whatever was in it. The formats went up a version for it: scan report 4, false-positive result 3, benchmark result 3. |
| 2026-11-20 | A rule bundle keeps its contents under ChaCha20 with the key in its header, as the quarantine keeps files, so that an antivirus does not take the bundle for the malware its rules describe. The key is the SHA-256 of the contents, so that the same rules give the same file. Bundles written before stay readable, and `warden rules build --plain` still writes one. This settles how a release stores its rules. |
| 2026-11-20 | The scan kit can carry a second rule bundle as a control, one that holds its rules as they are. One run on a machine then shows what its antivirus does with a bundle under the cipher and with one without. |
| 2026-11-20 | `RUSSIANPANDA_Purecrypter`, a rule written by hand, is the seventh on the exclusion list. It flagged a file of the Microsoft Defender app when the desktop's programs were scanned with administrator rights. |
| 2026-11-21 | A result names what it could not read. Where such a path would show which programs are installed on a private machine, the copy kept here replaces it and says so at its top, as evidence on the exclusion list may. Four paths in two results from the desktop are replaced. |
| 2026-11-21 | Phase 5 starts with a signature-trust check, by three routes: the embedded signature, the Windows catalog and the package signature. Persistence remediation follows as its second piece. |
| 2026-11-21 | A valid signature of a publisher on the trust list keeps a match of a published rule on record and out of the verdict. A hash match is always reported. |
| 2026-11-21 | A valid signature is not trust. The list starts with two identities of Microsoft, checks revocation, and says how a publisher gets on it. |
| 2026-11-21 | Once the check is measured, `RUSSIANPANDA_Purecrypter` comes off the exclusion list again and the scan of the desktop's programs with administrator rights is repeated to prove it. |
| 2026-11-21 | In the code and in reports the check is called trust, because "signature" already means a hash signature there. The engine states what it needs as a trait, and a crate of its own, `warden-trust`, answers; the engine never learns what a certificate is. |
| 2026-11-21 | Every rule of a rule bundle yields to a trusted signature, since Warden cannot tell a published rule from one its user wrote. Nothing else yields: not a hash match, not one of Warden's built-in rules, not what the heuristics say. The heuristic layer has flagged no clean file in any run, so nothing was measured that would need it. |
| 2026-11-21 | A trusted signature sets a rule match aside before the layers are combined. The match stays on record and is nobody's second sign. |
| 2026-11-21 | A file inside an archive and bytes in memory are never asked about. A signed file has room for data its signature does not cover, so the file around an archive vouches for nothing in it. |
| 2026-11-21 | A signature inside an executable counts only if the table that holds it holds one signature and nothing else. Windows accepts bytes added there unless an administrator switches a stricter check on; Warden does not. A file with such a table is not looked up in the catalogues, whose hash leaves the table out as well. A file that is no executable is trusted only as part of a package. |
| 2026-11-21 | A signature whose revocation could not be checked does not count, which is stricter than Windows. Windows may ask over the network; `--offline` keeps it from that. |
| 2026-11-21 | The check holds the file open against writing and compares its SHA-256 with the one the scan computed, so that its answer is about the bytes that were scanned. |
| 2026-11-21 | Where a clean file of a known publisher is flagged, the trust list is the first remedy and the exclusion list the second. A publisher gets on the trust list only for a false positive, with a real file as evidence, and by an anchor as narrow as it can be. |
| 2026-11-21 | The tests on Windows make their own certificates and tell the machine to trust two test roots. That happens on a GitHub-hosted runner, which is deleted after the job, and the script refuses to run anywhere else. ## Open decisions

- **Removing a file that is in use.** It was planned for phase 5, with the
  remediation. It only makes sense together with stopping the program that
  holds the file, and that takes the rights of the service. Proposed: it
  moves to phase 6. Until then a file that is in use is not quarantined,
  and the command says so.
- **Which rules a release ships.** Of the 5,137 rules in YARA Forge's core
  package, 2,055 name no licence. Building a bundle for one's own use is
  one thing; putting those rules into an installer is another. To be
  settled before the portfolio checkpoint (phase 8), when the first
  installer is built.
- **MalwareBazaar import with family names.** The plain hash-list import
  exists. Importing the CSV export, which carries malware family names,
  waits until it can be tested against a real export, which needs a free
  abuse.ch Auth-Key.
- **Windows endpoint security platform.** Microsoft announced general
  availability in November 2026. Whether a non-partner can use it is not
  documented publicly yet; to be checked before phase 13.
