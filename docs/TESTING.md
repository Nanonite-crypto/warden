# Testing

## The rule: no live malware

Warden is developed and tested without writing, generating, modifying or
handling live malware. Everything a test needs is one of these:

| Material | What it is | What it proves |
|---|---|---|
| EICAR test file | A harmless 68-byte string that every antivirus product detects on purpose | End-to-end detection, the demo |
| Inert fixtures | Harmless files generated by the tests. A test registers their hashes in a throwaway signature database, or writes a throwaway rule for a marker string it put in them | The mechanics of every layer |
| Public detection rules | The YARA Forge core package: rules that researchers have published. A rule describes malware, as byte patterns and conditions; it contains none | That a real rule set loads, runs within its limits and stays quiet on clean files |
| Clean files | Windows system files, the software on a CI runner, a Linux system tree | False-positive rate |
| Public feature data (from phase 3) | The EMBER2024 dataset: hashes, features and labels, no executables | Detection and false-positive rates of heuristics and the classifier |

### What this means for the numbers

Because no live samples are used, two things are deliberately **not
measured**, and the benchmarks say so instead of borrowing a figure:

- how many real-world malware files a given layer catches;
- an end-to-end detection rate on live samples.

What is measured: scan throughput, false positives on clean files, and (from
phase 3) detection and false-positive rates in feature space on EMBER2024's
held-out test period.

A rule set that flags nothing in clean files has shown that it is quiet,
not that it catches anything. That second half is exactly the part that
stays unmeasured here.

## Running the tests

```
cargo test --workspace
```

That runs unit tests, end-to-end scans of generated directory trees and
archives, property tests of the signature database and of the archive
unpacker, tests of the rule layer, and tests that drive the `warden` binary
the way a user would.

The same checks CI runs before anything is merged:

```
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo doc --workspace --no-deps --locked        (with RUSTDOCFLAGS=-D warnings)
cargo test --workspace --locked
```

On Windows, `scripts\win\check.cmd` builds the release binary, checks EICAR
detection, runs the tests and measures scan speed in one go. It writes its
results to `target\check\`. With `-Rules` it also downloads the pinned rule
package, builds the rule bundle and counts false positives in the Windows
system folder.

## EICAR in three forms

`warden eicar write <folder>` writes the test file three ways, one for each
thing that has to work:

| File | What it is | What catches it |
|---|---|---|
| `eicar.com` | The 68 bytes | Hash match, and the built-in rule |
| `eicar-padded.com` | The same with a line ending appended, which the definition of the test file allows | Only the built-in rule: the hash is a different one |
| `eicar.zip` | `eicar.com` inside a zip archive | Unpacking, then both layers |

The test string does not appear in this repository. The program assembles
it from two halves, and the built-in rule describes it as two patterns, so
that neither the source tree nor a built `warden.exe` is itself flagged by
other scanners. A test checks the rule file for it.

## EICAR and your antivirus

Two tests, and the demo, write the EICAR test file to disk and scan it. On a
machine with a resident antivirus (on Windows, Microsoft Defender) that file
is removed or locked within moments. That is correct behaviour, and it means
Warden never gets to see the file.

The tests are careful about where and when they do this:

- `WARDEN_EICAR_DIR` names a folder you have excluded from the antivirus.
  The tests then work inside it.
- Without that variable they use the system temporary folder, except on
  Windows, where they do not run at all. Every Windows machine has a
  resident antivirus, and `cargo test` should not set off its alarms.
- If the file cannot be written or read back, the test passes and prints a
  note saying it was not exercised.
- `WARDEN_REQUIRE_EICAR=1` turns "did not run" and "was blocked" into a
  failure. CI sets it on its Linux and Windows runners, together with a
  folder of its own, so the on-disk path is always tested there.

Detection of the EICAR bytes in memory is tested everywhere,
unconditionally.

### Excluding one folder from Microsoft Defender

This is a change to a security setting, so it is a step for you to take
knowingly, not something a script in this repository does for you. Exclude
only the dedicated test folder, never the whole repository or a drive.

From a PowerShell window opened as administrator, in the repository:

```powershell
Add-MpPreference -ExclusionPath "$PWD\testdata\eicar-zone"
```

`scripts\win\check.cmd` uses that folder and tells you if the exclusion is
missing. To undo it:

```powershell
Remove-MpPreference -ExclusionPath "$PWD\testdata\eicar-zone"
```

The `testdata` folder is ignored by git. The EICAR file is generated when
needed and deleted afterwards; it is never committed.

## Hostile input

Anything Warden parses is treated as hostile, because for a scanner it is.

- The signature database reader is tested against truncation at every
  header length, single-bit damage in every header byte, damage across the
  body, and deliberately crafted files whose digest is valid but whose
  structure is not. Property tests mutate valid databases, re-seal them with
  a correct digest, and require that the reader never panics and that an
  accepted database behaves like a sorted set.
- Text importers bound the length of a line, so a feed with one enormous
  line cannot exhaust memory.
- The archive unpacker is tested with archives built to cause trouble:
  nested deeper than the limit, with more members than the limit, with
  members larger than allowed, with a member that expands a thousandfold,
  with a bomb built from archives inside archives, with a directory that
  lists the same data two thousand times, password-protected,
  packed with a method the build does not know, cut off in the middle, and
  with a damaged tail. Every one must end in a report that says what was
  not checked and why, with nothing unpacked beyond the limits. A property
  test damages valid archives at random and requires the same.
- Names from inside an archive are attacker-controlled text. Control
  characters and the characters that reverse text direction are replaced
  before a name reaches a report or a terminal, and nothing is ever written
  to a path taken from an archive.
- The rule bundle reader is tested against truncation, damage in the header
  and the body, and bundles written for another version of the rule engine.
  A rule that does not compile is left out and named, and the rest of its
  file is kept.
- The exclusion list is a file that people edit by hand, so the reader is
  strict: an entry without evidence, a misspelt field, a hash of the wrong
  length or a rule named twice stops the build. So does an entry that would
  take out a rule that has to stay. A test loads the list in this
  repository, so a mistake in it fails in CI.
- A rule set that takes more than 30 seconds on one file is stopped, and
  the file is reported as checked in part.
- In the scan pipeline, a detector that panics costs one file, which is
  reported as skipped with the panic message. The scan carries on.

Fuzzing with `cargo-fuzz` starts in phase 3, when the first real file-format
parser (PE) arrives.

## False positives

```
warden false-positives <folder> --rules <bundle>
```

scans files that are expected to be clean and lists each one that gets a
verdict other than clean, with the rules that matched. It exits with 0 when
nothing was flagged and 1 otherwise, and `--output` saves the result as
JSON.

A count is only meaningful together with the rule set that produced it, so
every result records the bundle's digest, and the bundle records which rule
files it was built from and which rules were left out of it on purpose.
Results are in [BENCHMARKS.md](BENCHMARKS.md#false-positives).

A flagged file is not the end of a run but the start of a small
investigation: what is the file, and what in it does the rule match? A rule
that cannot tell a clean file from its target goes on the exclusion list,
[`rules/exclusions.toml`](../rules/exclusions.toml), with that file as
evidence, and the run is repeated. [RULES.md](RULES.md#rules-that-are-left-out)
describes the list. The scripts and workflows below build the bundle with
it; `scripts\win\check.cmd -Rules -AllRules` builds it without, which is
how the numbers from before an entry can be measured again.

Windows system files are scanned on a GitHub-hosted runner by the
`False positives` workflow. It reads many gigabytes from a slow disk, so it
runs when started by hand or when a branch named `fp-run/...` is pushed,
not on every change.

On your own Windows machine, `scripts\win\check.cmd -Rules` does the same
for the System32 folder. Microsoft Defender blocks the rule package it
downloads; [RULES.md](RULES.md#rule-files-and-your-antivirus) explains why,
and the one folder exclusion that this needs.

## Benchmarks

```
cargo bench -p warden-sigdb -p warden-engine     micro-benchmarks (Criterion)
warden bench <folder> --runs 3                   scan throughput on real files
```
